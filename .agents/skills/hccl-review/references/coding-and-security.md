# 检视规范：编码与安全

面向 PR 检视的编码规范要点（C/C++），供检视者与 AI Agent 逐条对照。规范全集以根目录 `AGENTS.md` 第 5 节、`.clang-format` 与 [CANN 编码规范](https://gitcode.com/cann/community/tree/master/contributor/coding-standards)为准，本文只列检视时必查的高频条目。规则适用于本仓全部 C/C++ 代码（`src/`、`experimental/`、`test/`、`examples/` 等）；对外头文件的命名一致性与接口对外必要性以 external-api.md 为准，本文件的命名与 UT 条款不评对外头文件，其余各节对对外头文件同样适用。检视纪律（只读、代码事实、工具验证、反证检验）与意见分级见 SKILL.md 的「检视纪律与意见分级」节。

## 判定原则

- **强制约束与经验建议分开**：标「红线/强制」的是仓内规范，按 CRITICAL/HIGH 报；纯风格与经验性规范按 MEDIUM/LOW 报。不要把强制项降成建议，也不要拿经验性偏好当红线。
- **级别与阻塞分开**：级别看缺陷本身的严重度；阻塞 = 本次 diff 引入且级别为 CRITICAL/HIGH。存量问题无论级别都不阻塞当次合入，级别照原样报，处置口径见 [SKILL.md](../SKILL.md)「移动代码与存量代码」。
- **看语义不看关键词**：结论来自完整控制流、数据流与调用链，不靠命中某个名字或某个 API 定罪。
- **交给工具的不重复挑**：格式、编译告警、静态可测的阈值由 `.clang-format`、clang-tidy 与门禁负责；检视只在工具覆盖不到或明显漏网时提。

## 命名（MEDIUM，经验建议）

命名要让人不看实现就能明白用途，并与模块既有术语一致。

- **风格**：类/函数 PascalCase，成员变量小驼峰 + 尾下划线，常量与宏 `UPPER_SNAKE_CASE`，文件名小写下划线，bool 用 `is`/`has`/`can` 前缀（同文件既有无前缀 bool 成员、或沿用同函数族既有形参名时不报）
- **语义判定**：只看名称能否表达用途、是否与模块术语一致，不按关键词命中。`tmp`/`data`/`info`/`value` 本身不是违规词；只有新定义的名字在当前上下文确实看不出对象与用途、又与模块术语不一致时才报，并给出改名候选；调用既有/框架 API 的名字不评
- **缩写**：以模块既有用法为准（同一模块出现 ≥3 次即视为既定）；检视者不认识的缩写先确认是否模块惯例，不按白名单机械匹配
- **函数名用「动词+对象」**：裸 `Process`/`Handle`/`Do`/`Func` 禁用；框架约定入口（如 AscendC/AIV kernel 的 `Process`）、返回同名成员的 getter、既有 `Do*` 执行函数族除外
- **名实一致**：`Get`/`Is` 类函数不得有对外可见的副作用，命中改为 `GetOrCreateXxx`/`EnsureXxx`；**坏命名不得靠注释弥补**——注释只解释意图，不替代名字自注释；对外接口名不达意受 ABI 约束不轻改名，属既定例外，按 external-api.md「兼容性与解耦」的兼容约束、以及 [SKILL.md](../SKILL.md)「死代码与注释代码」的仓内废弃流程（deprecate→宽限期→移除）处理并注明 rename 计划，不作为内部代码的通用豁免
- **类名表达职责**：`Manager`/`Util`/`Helper` 等通用后缀须前置具体职责（如 `HcclAlgoPluginMgr`）
- **同一概念沿用既有名**：不另造近义新名
- **不报的形态**：循环变量 `i`/`j`/`k`；`ret`/`rc` 承载错误码；类型名已表达语义的局部变量；`buf`/`data` 与 `count`/`size`/类型组合后语义清楚（如 `dataCount`）；常量表标识符
- **从宽**：仅凭签名一句话说不出用途的才报；检视者判定不一致时从宽不报；意见须附改名候选

## 格式、规模与清晰度（工具优先，人工兜底）

- 列宽 120、4 空格缩进、K&R 大括号、指针左对齐（`PointerAlignment: Left`）由 `.clang-format` 保证；CI 未拦且与周边明显不一致时才提 LOW。
- 函数超 50 行、参数超 6 个属静态可测的规模问题，优先由工具/门禁发现；人工只在明显该拆时按经验建议提，状态机、初始化序列这类确有必要的长函数不报。
- 清晰度仍靠人工判断：公共接口须有注释；魔法数字改用命名常量；同一含义不出现多种写法。

## C++11/14/17 特性使用（MEDIUM；lambda 生命周期 HIGH）

新特性按实际收益使用，不为炫技而用。

- **lambda 体量**：超 10 行且可独立命名 → 建议提取具名函数；标准算法短回调与测试内 lambda 除外
- **lambda 捕获不按语法一刀切**：会离开当前作用域的 lambda（被保存、注册成异步回调、入队、异步提交）禁 `[=]`/`[&]` 默认捕获，逐项列出；同步执行、不逃逸的短 lambda 用 `[=]`/`[&]` 不报；提交后立即 join/get/阻塞等待完成（含阻塞式 Submit）的跨线程 lambda 不按本行报，按下一行判定（其同步等待豁免同样适用）；同步 inline 回调（持锁访问器式回调、算法内部同步回调等由调用发起方等待返回的回调）不报
- **lambda 生命周期**：逃逸 lambda 的每项捕获都要核对其存活期——引用、`this`、`std::ref`/`std::reference_wrapper` 可能悬垂即报 HIGH；**值捕获指针只拷贝了地址，不保证指向对象仍存活**，同样要核对；提交方在同步等待完成之后才释放或离开捕获对象作用域的不报；捕获对象早于或并发于等待完成被销毁的（如先销毁再 join、等待期间离开作用域）仍按悬垂报 HIGH
- **模板**：多类型真实复用才用模板；仅 1 处实例化须说明必要性（其他分支、下游仓消费、规划用途）；业务代码深模板元编程须给普通写法对比；CRTP、`std::hash` 特化、转发引用属惯用法不报
- **auto**：类型冗长（迭代器/lambda/模板产物）或右侧一目了然才用；`auto x = GetData()` 遮蔽真实类型禁用；对外签名与对外头文件不用 auto（ABI）

合理使用不报：`constexpr`/`static const` 常量、结构化绑定、`if constexpr`、移动语义、不离开作用域的短谓词 lambda。

## 注释与死代码治理（MEDIUM）

注释解释「为什么」，不复述代码。

- **删除注释掉的代码**：需要历史时用 git 查询旧版本；对外头 API 用法示例、注明 Issue 的计划占位除外
- **删除 `#if 0` 等编译期禁用代码**：确需保留须注明 Issue
- **废话注释删除**：逐字复述代码的、与实现不符的过期注释；`@brief`/`@param`/`@return` 等规范头注释不属废话
- **注释要简明（LOW）**：表意不清、冗长绕口的注释按 LOW 建议改写清楚，意见附改写示例；复杂逻辑解释「为什么」而非「做什么」
- **不准随意添加 TODO/FIXME/HACK**：确有遗留事项须写成 `TODO(责任人): #Issue` 且 Issue 有效，否则删除
- **禁署名注释**：「修改人+日期」式注释删除，责任人用 git blame 查询

## 禁止仅为 UT 新增生产代码（MEDIUM）

生产代码的每个符号都要有生产用途。

- **新增生产符号须有生产使用证据**：函数/getter/可见性/编译分支无生产调用、且 PR 未说明后续调用方（附 PR/Issue 编号）即违规。生产使用含直接调用、生产构造/析构、虚函数 override 分派、回调/注册表/dlsym 绑定、模板实例化
- **全仓 grep 只是第一步，不能单独定罪**：跨仓调用、对外 API/ABI 导出符号、dlsym 动态查找、插件注册、虚函数分派、下游模板实例化在全仓 grep 里都不显示为调用；命中「无生产调用」后先按本行排除。grep 时排除定义处与死调用点，按全限定符号名核对调用方归属（生产 vs test）
- **测试专用改造同属违规**：仅测试需要的 friend 声明、`private`→`public` 提可见性、`forTest` 类默认参数
- **不报的形态**：依赖注入、protected virtual 覆写点、注册工厂、仓内既定测试访问授权（窄口子访问器文件）、与既有诊断/状态查询/回调接口同族（命名、所在文件、返回类型一致）且 PR 描述写明具体生产使用场景与调用方佐证（仅口头称「诊断用」而无场景或调用链路佐证的不豁免）、跨仓消费入口（附消费方证据）、仅替换依赖实现的编译分支

## 全局/静态可变状态与单例（HIGH，强制）

全局可变状态难测试、有初始化/析构时序风险，默认禁新增。

- **禁新增**：全局变量（含 `g_` 前缀、命名空间与匿名命名空间内可变变量）、文件/类/函数内 `static` 可变对象、函数内 `static` 局部对象式单例、单例访问器；`mutex`/`condition_variable`/`semaphore`/`atomic` 等纯同步原语不算可变状态（为修复竞态新增的锁/原子不报）；仅新增对既有全局/单例的调用不属新增（按锁/原子保护核查）
- **识别看状态不看名字**：`GetInstance`/`Instance` 只是线索；函数内 static 实例、全局 registry、宏展开的登记表都属此类。单例访问器指返回全局唯一对象的函数；形如 `GetXxxNum`/`GetInstanceCnt` 这类仅返回数值、不暴露共享对象引用的同前缀函数不算访问器（示意名，非仓内符号），UT 用例名也不算
- **确需新增须评审**：PR 描述说明理由并附评审通过结论（Discussion 纪要或权威评审人同意的 Issue/文档，普通任务 Issue 不算），检视者核实链接，未见即报 HIGH；优先改为实例成员或依赖注入
- **豁免逐项看条件**：`static const`/`constexpr` 值与常量表豁免，但其指针/引用指向可变对象不豁免；`thread_local` 不构成跨线程竞争——纯线程本地缓存（用前初始化、用后清理）豁免，只有线程池复用时状态残留会影响后续任务正确性（有证据）才按 MEDIUM 提；`once_flag`+`call_once` 只是初始化机制，被初始化的对象按对象本身判；static 函数、既有注册宏（`REGISTER_SELECTOR`/`REGISTER_ALG_ATTRS`/`REGISTER_EXECUTOR_IMPL` 等）展开的登记变量、通过既有注册宏新增的登记项、gtest 静态 fixture 属既定用法，不按本节报（仅新增自定义注册宏/登记表本身才按「禁新增」评审）
- **只拦新增，存量不清理**：既有可变全局/静态/单例不在本规则范围；检视中遇到的存量问题照规则级别提意见、不阻塞当次合入，量大另立 Issue 集中治理（处置口径见 [SKILL.md](../SKILL.md)「移动代码与存量代码」）；修改既有全局/静态时须核查锁/原子保护与初始化、析构时序
- **禁跨模块隐式传参**：不用全局变量在模块间传函数结果（如全局标志回传返回值）

## 内存与资源安全（红线，强制）

这类问题直接导致崩溃、泄漏或数据损坏，命中即报；判定要基于完整控制流、数据流与调用链，不做逐行机械检查。

| 检查项 | 判定要点 |
|--------|---------|
| 未初始化 | 使用点之前确实没有初始化路径才报。构造函数、出参、上游赋值都算初始化；「声明处没有显式初始化」本身不判错 |
| 空指针 | 找真实的空解引用路径：已判空、调用约定保证非空、上游已校验的不重复要求判空；返回指针的函数须读实现确认 null 分支 |
| 越界 | 索引与 `memcpy`/`memcpy_s` 长度须有边界来源与校验 |
| 整数溢出 | 有符号溢出不放过；显式窄化转换与 `size_t`/窄类型混算须核对截断、符号扩展与值域；无符号回绕看是否传导成长度、容量、偏移或循环条件的实际错误，仅回绕本身不判错 |
| 除零 | 除法/取模除数须有非零保证 |
| 资源泄漏 | 所有路径（含错误路径）Init/Cleanup 对称；RAII 或智能指针管理 |
| sizeof 误用 | 禁止对指针变量 sizeof 取数组大小；容器对象 sizeof ≠ 数据大小 |
| 安全函数（强制） | 生产代码（`src/`、`include/`、`experimental/`）中 `memcpy`/`sprintf`/`strcpy` 必须换用仓内要求的 `_s` 版本，并检查返回值、处理失败路径，不降为建议；`test/`、`examples/` 与 mock/桩代码不按「必须换用 `_s`」强制项报，但新增代码引入真实溢出/越界风险的，仍按本节「越界」红线报；仓内安全封装（内部已在调 `_s`）视为合规 |

## 并发安全（红线/经验）

共享可变状态的每次访问都要有同步保障；问题要看锁依赖、等待条件与释放路径，不是看到「持锁调用」就报。

- 全局/静态可变状态必须有锁、原子或屏障保护；检视时 grep 所有引用点确认访问线程
- **持锁期间做等待/阻塞操作不一律禁止**：核查是否存在反向加锁路径（死锁）、等待条件有无超时与唤醒保证（永久阻塞、线程饥饿）、等待期间是否还占着对方需要的资源（锁竞争）
- 同一组资源多把锁时确认加锁顺序一致；跨模块调用注意锁向外传递
- `thread_local`、不可变对象天然线程安全，可作误报排除依据
- 异步任务、回调与资源析构之间的生命周期检查见 [async-and-lifecycle.md](./async-and-lifecycle.md)

## 错误处理与异常安全（返回值与失败路径为强制，其余经验建议）

每个错误都要被正确表达、被检查，失败路径不漏清理。

- **系统调用/安全函数返回值必须检查；失败路径资源回滚完整**（强制，HIGH）
- **`noexcept` 只在确实不抛时才声明**（强制）：错误声明会让异常直接 `std::terminate`，比不标更危险；不要给可能抛异常的 `move`/`swap` 等操作硬加 `noexcept`（`delete` 表达式本身不抛异常；默认 `noexcept` 的析构里抛异常同样直接 terminate，无需再讨论 `noexcept`）
- 错误码语义准确：不得用 EAGAIN 表达「已存在」等易误导语义（MEDIUM）
- **`catch(...)` 本身不判违规**（MEDIUM）：资源清理、兜底日志是正当用法；看捕获后是否既不恢复、也不上报、也不再抛——那才是吞错误
